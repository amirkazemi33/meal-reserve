# یوزکیس‌های سامانه رزرو غذا (Meal Reserve)

این سند برای **تیم فنی و محصول** است و امکانات فعلی سامانه و روند هر یوزکیس را بر اساس پیاده‌سازی موجود توصیف می‌کند.

> راهنمای ساده برای کاربران غیر فنی: [`user-guide.md`](./user-guide.md)

---

## ۱. نمای کلی محصول

سامانه برای رزرو غذای سازمانی است. کاربر منوی هفتگی را می‌بیند، برای هر روز و هر وعده غذا رزرو می‌کند، می‌تواند لغو کند، سابقه را ببیند و نظر بدهد. ادمین و کترینگ منو، غذاها، کاربران، نقش‌ها و گزارش‌ها را مدیریت می‌کنند.

**هفته کاری:** از شنبه شروع می‌شود.

**مهلت رزرو (Cutoff):** برای تاریخ `D`، رزرو تا ساعت مشخص‌شده در روز `D−1` باز است. امروز و گذشته همیشه بسته هستند. مقدار پیش‌فرض: `16:00`.

**واحد رزرو:** یک رکورد به ازای `(کاربر + تاریخ + وعده)`. برای همان اسلات، تغییر غذا/افزودنی با upsert انجام می‌شود.

## ۳. نقش‌ها و دسترسی‌های پیش‌فرض

### مدیر سیستم (`admin`)
همه دسترسی‌ها.

### کارمند (`employee`)
- `reservation.create` — ثبت رزرو / مشاهده منو و سابقه
- `reservation.cancel` — لغو رزرو
- `feedback.create` — ثبت نظر

### کترینگ (`catering`)
- `menu.manage` — ساخت منو
- `food.manage` — مدیریت غذاها
- `meal_period.manage` — مدیریت وعده‌ها
- `report.cooking` — آمار پخت

### دسترسی‌های اختیاری (معمولاً فقط برای ادمین یا نقش سفارشی)
| کد | قابلیت |
|----|--------|

| `reservation.for_others` | رزرو برای دیگران |
| `user_list.manage` | مدیریت لیست کاربران |

| `report.reservations` | مدیریت/گزارش رزروها |
| `settings.cutoff` | تنظیم ضرب‌الاجل |

## ۴. قوانین کسب‌وکار مشترک

1. کاربر باید فعال (`isActive`) باشد؛ در غیر این صورت نشست نامعتبر و هدایت به خروج.
2. منو فقط آیتم‌های ثبت‌شده برای تاریخ + وعده را نشان می‌دهد.
3. فقط غذای نوع `MAIN` پایه رزرو است؛ `DRINK` و `YOGURT_SALAD` اختیاری‌اند و باید همان تاریخ/وعده باشند.
4. لغو نرم است (`CANCELLED`)؛ رزرو مجدد همان اسلات را دوباره `ACTIVE` می‌کند.
5. محل تحویل پیش‌فرض = محل تحویل پروفایل کاربر؛ تغییر محل فقط با دسترسی مربوطه.
6. تعداد پیش‌فرض `1` است (بازه مجاز در صورت دسترسی: ۱ تا ۹۹).
7. سقف ظرفیت/موجودی برای هر غذا وجود ندارد.
8. تغییر نقش/دسترسی تا لاگین مجدد در JWT اعمال نمی‌شود.
9. ساعت شروع/پایان وعده فقط متادیتا است؛ باز/بسته بودن رزرو فقط با cutoff تعیین می‌شود.

## ۵. یوزکیس‌های احراز هویت

### UC-01 — ورود به سامانه
- **بازیگر:** مهمان
- **پیش‌شرط:** داشتن شماره موبایل و رمز عبور فعال
- **جریان اصلی:**
  1. کاربر به `/login` می‌رود.
  2. شماره و رمز را وارد می‌کند.
  3. در صورت صحت، کوکی نشست JWT ساخته می‌شود (اعتبار حدود ۷ روز).
  4. کاربر به `/menu` هدایت می‌شود.
- **جایگزین:**
  - اگر نقش کاربر دسترسی منو نداشته باشد، به مسیر مناسب (مثلاً ساخت منو یا آمار پخت) یا لاگین برمی‌گردد.
  - کاربر غیرفعال یا اطلاعات اشتباه → خطا / عدم ورود.
- **نتیجه:** نشست معتبر و دسترسی به صفحات مجاز.

### UC-02 — خروج از سامانه
- **بازیگر:** کاربر لاگین‌شده
- **جریان اصلی:**
  1. از هدر روی «خروج» کلیک می‌کند (یا مسیر `/logout`).
  2. کوکی نشست پاک می‌شود.
  3. به صفحه لاگین هدایت می‌شود.
- **نتیجه:** پایان نشست.

### UC-03 — محافظت از مسیرها
- **بازیگر:** سامانه
- **جریان اصلی:**
  1. درخواست به مسیر غیرعمومی می‌رسد.
  2. اگر کوکی معتبر نباشد → هدایت به `/login`.
  3. مسیرهای عمومی مثل `/login` و `/logout` بدون نیاز به نشست در دسترس‌اند.
- **نتیجه:** صفحات داخلی فقط برای کاربران احراز هویت‌شده.

## ۶. یوزکیس‌های رزرو کارمند

### UC-10 — مشاهده منوی هفتگی / روزانه
- **بازیگر:** کاربر با `reservation.create`
- **مسیر:** `/menu`
- **جریان اصلی:**
  1. کاربر وارد منو می‌شود.
  2. هفته‌های دارای منو را می‌بیند؛ می‌تواند هفته قبل/بعد را جابه‌جا کند.
  3. می‌تواند بین «نمای هفته» و «روزانه» سوئیچ کند.
  4. برای هر روز وضعیت «باز / بسته»، برچسب «امروز» و «قابل رزرو» (اولین روز هنوز قابل رزرو) نمایش داده می‌شود.
  5. زیر هر روز، وعده‌ها و آیتم‌های غذا (اصلی / نوشیدنی / ماست و سالاد) و رزرو فعلی کاربر دیده می‌شود.
- **نتیجه:** تصویر کامل از منو و وضعیت رزرو خودش.

### UC-11 — ثبت / تغییر رزرو غذای اصلی
- **بازیگر:** کاربر با `reservation.create`
- **پیش‌شرط:** روز هدف هنوز قبل از cutoff باز باشد؛ آیتم منو از نوع اصلی باشد.
- **جریان اصلی:**
  1. کاربر در روز و وعده موردنظر روی «انتخاب» یک غذای اصلی کلیک می‌کند.
  2. سیستم رزرو را upsert می‌کند (ایجاد یا به‌روزرسانی اسلات `(کاربر، تاریخ، وعده)`).
  3. وضعیت `ACTIVE` می‌شود؛ غذای اصلی (و در صورت وجود افزودنی‌های قبلی/فعلی) ذخیره می‌شود.
  4. صفحه منو و صفحات مرتبط بازخوانی می‌شوند.
- **جایگزین:**
  - روز بسته / گذشته از cutoff → خطا.
  - آیتم نامعتبر یا غیر اصلی → خطا.
- **نتیجه:** رزرو فعال برای آن وعده.

### UC-12 — انتخاب نوشیدنی / ماست و سالاد
- **بازیگر:** کاربر با `reservation.create`
- **پیش‌شرط:** قبلاً (یا همزمان با) غذای اصلی برای همان اسلات مشخص شده باشد.
- **جریان اصلی:**
  1. کاربر افزودنی را انتخاب می‌کند یا «بدون …» را می‌زند.
  2. سیستم همان رزرو را با `drink` / `side` به‌روز می‌کند.
- **نتیجه:** افزودنی‌ها روی رزرو ثبت می‌شوند.

### UC-13 — تغییر تعداد (اختیاری)
- **بازیگر:** کاربر با `reservation.quantity`
- **جریان اصلی:**
  1. کنار عنوان وعده، تعداد را تغییر می‌دهد.
  2. پس از مکث کوتاه، مقدار ذخیره می‌شود (۱–۹۹).
- **نتیجه:** `quantity` رزرو به‌روز می‌شود.

### UC-14 — انتخاب محل تحویل هنگام رزرو (اختیاری)
- **بازیگر:** کاربر با `reservation.select_delivery_location`
- **جریان اصلی:**
  1. لیست محل‌های فعال را می‌بیند.
  2. محل را انتخاب می‌کند؛ مقدار همراه ذخیره رزرو بعدی (غذا/افزودنی/تعداد) اعمال می‌شود.
- **بدون این دسترسی:** محل تحویل پروفایل کاربر استفاده می‌شود.

### UC-15 — لغو رزرو از منو
- **بازیگر:** کاربر با `reservation.cancel`
- **پیش‌شرط:** رزرو فعال برای اسلات وجود داشته باشد؛ روز هنوز باز باشد.
- **جریان اصلی:**
  1. کاربر روی «لغو» کلیک می‌کند.
  2. وضعیت رزرو `CANCELLED` می‌شود.
- **نتیجه:** اسلات آزاد برای رزرو مجدد (با upsert بعدی).

### UC-16 — مشاهده و مدیریت سابقه رزرو
- **بازیگر:** کاربر با `reservation.create` (صفحه سابقه)
- **مسیر:** `/history`
- **جریان اصلی:**
  1. لیست رزروهای خود (فعال و لغوشده) را می‌بیند.
  2. در صورت داشتن دسترسی و باز بودن مهلت، می‌تواند وضعیت را تغییر دهد (لغو / فعال‌سازی مجدد طبق اکشن‌های موجود).
- **نتیجه:** پیگیری تاریخچه شخصی.

## ۷. یوزکیس بازخورد

### UC-20 — ثبت نظر برای غذا
- **بازیگر:** کاربر با `feedback.create`
- **مسیر:** `/feedback`
- **پیش‌شرط:** رزرو `ACTIVE` مربوط به امروز یا گذشته؛ امتیاز ۱ تا ۵.
- **جریان اصلی:**
  1. کاربر رزرو واجد شرایط را انتخاب می‌کند.
  2. امتیاز و در صورت تمایل توضیح ثبت می‌کند.
  3. نظر ذخیره یا به‌روز می‌شود (یک نظر به ازای هر رزرو).
- **نتیجه:** بازخورد به رزرو لینک می‌شود.

## ۸. یوزکیس‌های کترینگ / مدیریت محتوا

### UC-30 — مدیریت وعده‌ها
- **دسترسی:** `meal_period.manage` — `/admin/meal-periods`
- **جریان:** ایجاد/ویرایش وعده (عنوان، ساعت شروع/پایان، توضیح، فعال بودن، ترتیب نمایش).
- **نتیجه:** وعده‌ها برای منو و رزرو در دسترس‌اند.

### UC-31 — مدیریت غذاها
- **دسترسی:** `food.manage` — `/admin/foods`
- **جریان:** ثبت غذا با نوع `MAIN` / `DRINK` / `YOGURT_SALAD`، توضیح، فعال/غیرفعال.
- **نتیجه:** کاتالوگ غذا برای ساخت منو.

### UC-32 — ساخت منوی روزانه/هفتگی
- **دسترسی:** `menu.manage` — `/admin/menu`
- **جریان:**
  1. تاریخ و وعده انتخاب می‌شود.
  2. غذاهای موردنظر به عنوان `MenuItem` برای آن تاریخ+وعده ست می‌شوند.
  3. بازنویسی منو آیتم‌های قبلی آن اسلات را جایگزین می‌کند.
- **نکته:** حذف آیتم منو ممکن است ارجاع `menuItemId` رزروهای قبلی را null کند؛ `foodId` رزرو باقی می‌ماند.
- **نتیجه:** منوی قابل نمایش و رزرو برای کارمندان.

### UC-33 — مدیریت محل‌های تحویل
- **دسترسی:** `delivery_location.manage` — `/admin/delivery-locations`
- **جریان:** تعریف محل (عنوان، آدرس، توضیح، فعال/غیرفعال).
- **نتیجه:** محل‌ها برای پروفایل کاربر و رزرو.

### UC-34 — تنظیم ضرب‌الاجل رزرو
- **دسترسی:** `settings.cutoff` — `/admin/settings`
- **جریان:** مقدار ساعت cutoff (مثل `16:00`) ذخیره می‌شود.
- **نتیجه:** بازه زمانی مجاز رزرو در کل سامانه تغییر می‌کند.

### UC-35 — مشاهده آمار پخت
- **دسترسی:** `report.cooking` — `/cooking-report`
- **جریان:** تجمیع تعداد رزروهای فعال بر اساس غذا/تاریخ/وعده برای برنامه‌ریزی پخت.
- **نتیجه:** گزارش عملیاتی آشپزخانه.

## ۹. یوزکیس‌های مدیریت کاربران و دسترسی

### UC-40 — مدیریت کاربران
- **دسترسی:** `users.manage` — `/admin/users`
- **جریان:** ایجاد/ویرایش کاربر (نام، شماره، رمز، محل تحویل پیش‌فرض، نقش‌ها، فعال/غیرفعال)، حذف در صورت پشتیبانی UI.
- **نتیجه:** حساب‌های قابل لاگین با نقش مشخص.

### UC-41 — مدیریت نقش‌ها و دسترسی‌ها
- **دسترسی:** `roles.manage` — `/admin/roles`
- **جریان:** تعریف نقش و تخصیص مجموعه Permissionها.
- **نتیجه:** کنترل دسترسی منوها و اکشن‌ها.

### UC-42 — مدیریت لیست کاربران
- **دسترسی:** `user_list.manage` — `/admin/user-lists`
- **جریان:**
  1. مالک لیست، لیست با عنوان/توضیح می‌سازد.
  2. اعضا را اضافه/حذف/همگام می‌کند.
- **نتیجه:** گروه‌بندی کاربران برای رزرو گروهی.

## ۱۰. یوزکیس‌های رزرو نمایندگی و گزارش ادمین

### UC-50 — رزرو برای دیگران
- **دسترسی:** `reservation.for_others` — `/admin/reserve-for`
- **پیش‌شرط اختیاری:** برای انتخاب از لیست، `user_list.manage`
- **جریان اصلی:**
  1. ادمین کاربران یا یک لیست کاربری را انتخاب می‌کند.
  2. برای هر نفر، انتخاب غذا (و در صورت دسترسی، محل/تعداد/افزودنی) را مشخص می‌کند.
  3. سیستم برای هر ورودی همان قوانین cutoff و کاربر فعال را اعمال می‌کند.
  4. نتیجه موفق/ناموفق به‌ازای هر مورد برگردانده می‌شود.
- **نتیجه:** رزروهای فعال به نام کاربران هدف.

### UC-51 — مدیریت و گزارش رزروها
- **دسترسی:** `report.reservations` — `/admin/reports`
- **جریان:**
  1. مشاهده لیست رزروها با جزئیات کاربر، غذا، وعده، محل، تعداد، وضعیت.
  2. ویرایش/لغو/تغییر محل توسط ادمین (در این مسیر، محدودیت cutoff برای تغییر وضعیت می‌تواند دور زده شود).
- **نتیجه:** کنترل عملیاتی رزروها در سطح سازمان.

## ۱۲. جریان سرتاسری نمونه (کارمند)

```text
ورود (/login)
  → مشاهده منوی هفته (/menu)
  → انتخاب غذای اصلی برای فردا (قبل از cutoff)
  → (اختیاری) نوشیدنی / ماست و سالاد / تعداد / محل تحویل
  → در صورت نیاز لغو از منو یا سابقه
  → پس از مصرف، ثبت نظر (/feedback)
  → خروج
```

## ۱۳. جریان سرتاسری نمونه (کترینگ)

```text
ورود
  → تعریف وعده و غذا
  → ساخت منو برای روزهای آینده
  → مشاهده آمار پخت برای آماده‌سازی
```

## ۱۴. جریان سرتاسری نمونه (مدیر)

```text
ورود
  → مدیریت کاربران و نقش‌ها
  → تنظیم cutoff و محل‌های تحویل
  → رزرو برای دیگران در صورت نیاز
  → پایش و اصلاح رزروها از گزارش‌ها
```

## ۱۵. خارج از محدوده فعلی محصول

این موارد در پیاده‌سازی فعلی وجود ندارند و یوزکیس رسمی ندارند:

- سقف ظرفیت / موجودی برای هر غذا
- محدودیت «فقط یک وعده در روز» (الان چند وعده در یک روز مجاز است)
- API REST عمومی برای رزرو
- پرداخت آنلاین یا کیف پول
- اعلان پیامکی/ایمیلی خودکار برای یادآوری cutoff

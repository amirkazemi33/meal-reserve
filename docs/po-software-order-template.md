# قالب مستندسازی سفارش نرم‌افزار (برای Product Owner)

این فایل را به PO بدهید.

**هدف:** وقتی نرم‌افزاری سفارش می‌دهید یا فیچر جدیدی می‌خواهید، قبل از شروع توسعه، نیاز را با **همین فرمت** بنویسید. این کار جلوی ابهام، دوباره‌کاری و سوءتفاهم بین کسب‌وکار و تیم فنی را می‌گیرد.

**مخاطب این قالب:** Product Owner / صاحب محصول / سفارش‌دهنده  
**خروجی مورد انتظار:** یک سند پرشده که تیم فنی بتواند از روی آن تحلیل، تخمین و پیاده‌سازی کند.

---

## نحوه استفاده

1. یک کپی از این فایل بگیرید (مثلاً `docs/orders/ORDER-YYYYMMDD-عنوان.md`).
2. بخش‌های راهنما را بخوانید و قسمت‌های `[داخل براکت]` را پر کنید.
3. چیزی را که نمی‌دانید خالی نگذارید؛ بنویسید **«نامشخص — باید تصمیم گرفته شود»**.
4. قبل از شروع اسپرینت، سند را با تیم فنی مرور و تأیید کنید.

## ۱. خلاصه یک‌صفحه‌ای (Elevator Pitch)

در ۳ تا ۵ جمله بنویسید:

- این نرم‌افزار / فیچر **چیست؟**
- **چه مشکلی** را حل می‌کند؟
- **چه کسی** از آن استفاده می‌کند؟
- بعد از تحویل، **چه چیزی بهتر می‌شود؟**

**نمونه خوب:**  
«سامانه‌ای برای رزرو غذای کارکنان که منوی هفته را نشان می‌دهد، تا ساعت مشخصی روز قبل امکان رزرو/لغو می‌دهد، و به کترینگ آمار پخت می‌دهد تا دورریز کمتر شود.»

**نمونه بد:**  
«یک اپ خوب برای غذا می‌خواهیم.»

## ۵. امکانات (Feature List)

لیست امکانات را **به زبان کاربر** بنویسید، نه به زبان فنی.

| کد | امکان | نقش استفاده‌کننده | اولویت (Must / Should / Could) | توضیح کوتاه |
|----|--------|-------------------|--------------------------------|-------------|
| F-01 | مشاهده منوی هفته | کارمند | Must | [...] |
| F-02 | رزرو غذا | کارمند | Must | [...] |
| F-03 | آمار پخت | کترینگ | Should | [...] |

**تعریف اولویت‌ها:**

- **Must:** بدون آن محصول قابل استفاده نیست
- **Should:** مهم است ولی می‌شود فاز بعد
- **Could:** خوب است اگر وقت بود

## ۶. جریان‌های اصلی (User Journeys)

برای هر کار مهم کاربر، یک جریان ساده بنویسید. لازم نیست UML بلد باشید.

### جریان: [مثلاً رزرو غذا توسط کارمند]

- **هدف کاربر:** [غذای فردا را رزرو کند]
- **پیش‌نیاز:** [حساب فعال داشته باشد / منو ساخته شده باشد]
- **مراحل:**
  1. وارد سامانه می‌شود
  2. منوی هفته را می‌بیند
  3. روز و وعده را انتخاب می‌کند
  4. غذا را رزرو می‌کند
  5. تأیید را می‌بیند
- **نتیجه موفق:** [رزرو ثبت شده و در سابقه دیده می‌شود]
- **اگر خطا شد چه؟**
  - منو خالی باشد → [پیام مناسب]
  - مهلت گذشته باشد → [روز بسته باشد و دکمه غیرفعال]

> حداقل ۳ تا ۵ جریان اصلی برای محصول کافی است؛ بقیه را می‌توان بعداً افزود.

## ۷. قوانین کسب‌وکار (Business Rules)

این بخش خیلی مهم است. هر قانون را شفاف و قطعی بنویسید.

| کد | قانون | مثال |
|----|--------|------|
| BR-01 | [رزرو فقط تا ساعت X روز قبل مجاز است] | [برای سه‌شنبه تا دوشنبه ۱۶:۰۰] |
| BR-02 | [هر کاربر در هر روز و هر وعده فقط یک رزرو فعال دارد] | [عوض کردن غذا = به‌روزرسانی همان رزرو] |
| BR-03 | [...] | [...] |

سوال‌هایی که حتماً جواب دهید:

- مهلت / ددلاین دارید؟
- محدودیت تعداد دارید؟
- لغو مجاز است؟ تا کی؟
- چه چیزی یکتا است؟ (مثلاً یک رزرو به ازای هر وعده)
- چه نقش‌هایی از قانون مستثنی‌اند؟ (مثلاً ادمین)

اگر قانون مشخص نیست، صریحاً بنویسید: **«نیاز به تصمیم PO»**.

## ۸. داده و موجودیت‌های اصلی (به زبان ساده)

## ۱۴. پذیرش و تحویل (Acceptance)

برای هر امکان Must، شرط پذیرش بنویسید تا اختلاف سلیقه کمتر شود.

### مثال پذیرش برای «رزرو غذا»
- [ ] کاربر می‌تواند برای روز باز، غذای اصلی رزرو کند
- [ ] بعد از cutoff، دکمه رزرو کار نمی‌کند / روز بسته است
- [ ] رزرو در صفحه سابقه دیده می‌شود
- [ ] لغو قبل از مهلت ممکن است

**تعریف Done این سفارش:** همه آیتم‌های Must در محیط توافق‌شده تست و تأیید شده‌اند.

# چک‌لیست قبل از تحویل سند به تیم فنی

- [ ] خلاصه محصول در چند جمله واضح است
- [ ] نقش‌ها مشخص‌اند
- [ ] In Scope و Out of Scope جدا شده‌اند
- [ ] امکانات اولویت‌بندی شده‌اند (Must/Should/Could)
- [ ] حداقل ۳ جریان اصلی نوشته شده
- [ ] قوانین کسب‌وکار قطعی یا صریحاً «نیاز به تصمیم» هستند
- [ ] معیار پذیرش برای Mustها نوشته شده
- [ ] سوالات باز لیست شده‌اند

اگر بیش از ۲ مورد از موارد بالا ناقص است، سند هنوز برای شروع توسعه آماده نیست.

# پیوست الف — چیزهایی که PO نباید در این سند بنویسد

این‌ها کار تیم فنی است؛ مگر اینکه محدودیت کسب‌وکاری قطعی داشته باشید:

- نام دیتابیس، ORM، فریمورک
- جزئیات API و اسکیما جداول
- انتخاب کتابخانه UI
- معماری میکروسرویس و ...

PO باید بگوید **چه می‌خواهیم و چرا**؛ تیم فنی می‌گوید **چطور می‌سازیم**.

---

# پیوست ب — تفاوت این سند با راهنمای کاربر و یوزکیس فنی

| سند | مخاطب | هدف |
|-----|--------|------|
| **همین قالب سفارش (PRD سبک)** | PO → تیم فنی | تعریف نیاز قبل از ساخت |
| یوزکیس فنی | تیم فنی/محصول | تحلیل دقیق رفتار سیستم |
| راهنمای کاربر | کاربر نهایی | آموزش استفاده بعد از ساخت |

ترتیب پیشنهادی:

1. PO با این قالب سفارش را می‌نویسد  
2. تیم فنی در صورت نیاز به یوزکیس/تحلیل تبدیل می‌کند  
3. بعد از ساخت، راهنمای کاربر برای آموزش نوشته می‌شود  

---

*این قالب عمومی است و وابسته به یک محصول خاص نیست. برای هر سفارش نرم‌افزار یا فیچر بزرگ، یک نسخه پرشده جداگانه بسازید.*
